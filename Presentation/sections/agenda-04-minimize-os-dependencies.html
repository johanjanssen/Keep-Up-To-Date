☕ Ride the Release Train

Modern runtimes and languages ship on a predictable cadence — not when they feel ready, but on a fixed schedule.

  • Regular releases → smaller, manageable changes each time
  • LTS (Long-Term Support) releases get extended security patches — safe for production
  • Non-LTS releases are production-quality for short-lived or internal services

🎬 Demo: Free Performance from Upgrading Java

Same code, same hardware — JMH benchmarks across Java 17 → 25 → 28 EA

☕ Java 17 → 25 — zero code changes
  • Compact Object Headers (JEP 519, stable since 25) shrink every object header — less heap for boxed values & small records
  • Virtual Threads (JEP 444) remove the thread-per-task memory ceiling for I/O-bound workloads — the biggest, most reliable win in the suite
  • Math-heavy code measured ~40% faster (mathHeavyComputation), JIT/runtime improvements only
🔮 Java 25 → 28 EA — Valhalla preview Same benchmark, one keyword: record Point → value record Point. Verified (not assumed from the JEP): ~60% less memory and 4-8x faster — but only once fields are narrow enough to fit the JVM's current flattening size limit.

It's Not Just a Java Problem

Every language faces the same "does my image need a full runtime?" question — the shape of the answer just differs.

LanguageSmall-image lever
Javajlink custom JRE, or GraalVM native-image (AOT) to drop the JVM entirely
.NETNative AOT — .NET's direct equivalent of GraalVM native-image
GoCompiles to a single static binary by default — scratch "just works"
RustSame story as Go with a musl target — static binary, no runtime image needed
Python / Node.jsInterpreted — always need a runtime layer; lever is -slim / -alpine / distroless base images

Java and .NET need an explicit AOT step to reach what Go and Rust get by default; interpreted languages can't get there at all — only smaller.
