Vendor JRE vs. Custom jlink Runtime

Both drop the compiler and dev tools a full JDK carries: a runtime-only image. They trade off differently.

Vendor JRE image

  • 📦Every standard module included: bigger image
  • ⚡Vendor tuning (e.g. a pre-built CDS archive) can lower startup CPU/memory per launch
  • ✅Zero build effort: just pull the tag

Custom jlink runtime

  • ✂️Only the modules your app uses: smaller image
  • ⚠️No vendor pre-optimization; you own the build step
  • 🕵️Miss a reflectively-used module → runtime failure

Building a Custom jlink Runtime

Two commands: find what you use, then link only that

☕ Java example 
jdeps --print-module-deps --ignore-missing-deps app.jar    # 1. find required modules
jlink --add-modules $(cat modules.txt) --strip-debug \     # 2. build the slim runtime
      --no-header-files --no-man-pages --output custom-jre

Rule of thumb: start with a vendor JRE image; reach for jlink once size actually matters (edge, serverless, embedded).

It's Not Just a Java Problem

Every language faces the same "does my image need a full runtime?" question: the shape of the answer just differs.

LanguageSmall-image lever
Javajlink custom JRE, or GraalVM native-image (AOT) to drop the JVM entirely
.NETNative AOT: .NET's direct equivalent of GraalVM native-image
GoCompiles to a single static binary by default: scratch "just works"
RustSame story as Go with a musl target: static binary, no runtime image needed
Python / Node.jsInterpreted: always need a runtime layer; lever is -slim / -alpine / distroless base images

Java and .NET need an explicit AOT step to reach what Go and Rust get by default; interpreted languages can't get there at all, only smaller.
