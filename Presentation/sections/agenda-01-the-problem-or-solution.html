🚨 The "It Works, Don't Touch It" Trap

"Projects don't drift maliciously — just one sprint at a time."

  • 🧩Every application has direct and transitive dependencies — often hundreds
  • ✅You consciously chose a small fraction of them
  • 🎲The rest came with the territory — and each carries potential CVEs
☕ Java example
A typical Spring Boot app: 50–80 direct, 200–400 transitive dependencies.
./mvnw dependency:tree | wc -l — prepare to be surprised.

The Compounding Cost of Delay

  • 🔐Security: each skipped version = another version to jump over when a CVE forces your hand
  • ⚡Performance: runtime improvements accumulate — you leave free speed on the table
  • 🧗Migration effort: small incremental hops are easy; multi-year jumps require dedicated projects
☕ Java 17 → 25 — zero code changes
  • Compact Object Headers (JEP 519, stable since 25) shrink every object header — less heap for boxed values & small records
  • Virtual Threads (JEP 444) remove the thread-per-task memory ceiling for I/O-bound workloads — the biggest, most reliable win in the suite
  • Math-heavy code measured ~40% faster (mathHeavyComputation), JIT/runtime improvements only
☕ Java example
Java 8 → 21 in one jump: complex module-system breakage, API removals, GC changes.
Java 8 → 11 → 17 → 21 incrementally: each hop is manageable and well-documented.

"If it hurts, do it more often." — Martin Fowler

🔍 Two Layers of Scanning

They find different things — you need both

Layer 1: Source / Build Time

What you declared

  • 📄Scans your dependency manifest
  • ⚡Fast, integrates with CI
  • ⚠️Misses OS-level and transitive-only packages

Layer 2: Runtime / Image

What actually ships

  • 🐳Scans OS packages + language libs in the artifact
  • 🔎Finds what build-time scanning misses
  • 🎯Closer to what attackers see
☕ Java example Layer 1: OWASP Dependency Check scans pom.xml. Layer 2: Trivy / Grype scan the Docker image (OS pkgs + all JARs). A transitive JAR pulled in by a framework won't appear in Layer 1 if it's not declared.

Source-Level Scanning

Scan dependency manifests against a vulnerability database as part of the build. Fail the build on high-severity findings.

☕ OWASP Dependency Check

Analyzers for Java (Maven/Gradle), .NET, Node.js, Python and Ruby — this demo uses the Maven plugin.

<plugin>
    <groupId>org.owasp</groupId>
    <artifactId>dependency-check-maven</artifactId>
    <configuration>
        <failBuildOnCVSS>7</failBuildOnCVSS>  <!-- fail on HIGH+ -->
    </configuration>
</plugin>
./mvnw dependency-check:check
# log4j-core-2.0.jar      → CVE-2021-44228 CRITICAL 10.0 🔴
# jackson-databind-2.9.10 → CVE-2019-14379 CRITICAL  9.8 🔴

Image / Artifact Scanning

Scan the built artifact — container image, fat JAR, etc. — for vulnerabilities in the OS layer and bundled dependencies. These scanners are language-agnostic: they inspect the artifact itself, not a build file.

🌐 Grype (Anchore)
  • Generic — any container image
  • Fast, offline-capable
  • SARIF → GitHub Security tab
🌐 Trivy (Aqua)
  • Generic — any container image
  • Secrets & misconfig scanning
  • Widest DB coverage
🌐 OSV-Scanner (Google)
  • Generic — images, lockfiles & SBOMs, 20+ ecosystems
  • One tool, one database: OSV.dev
  • Also scans source manifests — see Layer 1

One Scanner, Every Ecosystem: OSV-Scanner

Grype and Trivy scan built images; OWASP Dependency Check scans the manifest. OSV-Scanner (Google / OSV.dev) takes a third path — one CLI that reads lockfiles, SBOMs and images across 20+ ecosystems, all against the same open OSV database.

🌐 osv-scanner 
osv-scanner scan source --lockfile=pom.xml .
osv-scanner scan image eclipse-temurin:25-jre
osv-scanner scan --sbom=target/bom.json .
Same DB, same tool, whether you're scanning a Java pom.xml, a Python requirements.txt, a Go go.sum, or the built image.

Different Scanners, Different Results

Different databases, different scan targets → different findings

  • 🌐Grype & Trivy — separate feeds, scan the built image
  • 🌐OSV-Scanner — the OSV.dev database, scans lockfiles, SBOMs and images
  • ☕OWASP Dependency Check — the NVD database, scans the manifest at build time

No two tools agree on every finding. Run more than one for full coverage.

🔥 When Drift Becomes a Crisis: Log4Shell

Dec 2021 — a logging library nobody had looked at in years

10.0CVSS score — the maximum possible
93%of cloud environments exposed
2 hrsfor the vendor to ship a patch
Weeksfor most teams to actually deploy it
The bill: billions of dollars in remediation, lost productivity, and follow-on attacks — fixing it consumed up to 12% of some organizations' entire annual IT, application-development, and security budgets, all for one transitive dependency.

Root cause: not a bug anyone wrote — a library nobody had reviewed in years, several layers down in the dependency tree.

😱 It Wasn't a One-Off: Spring4Shell

2022 — same pattern, a different framework

  • CVE-2022-22965 — a critical RCE in the Spring framework itself, not a bundled library this time
  • Teams on old Spring versions couldn't patch directly — they had to upgrade the framework first

The version gap turned a one-day fix into a multi-week project.

How's Your Situation?

  • ❓Do you know what operating system (version) you're using?
  • ❓Do you know which operating system packages (versions) you're using?
  • ❓Do you know which libraries (versions) you're packaging in your application?
  • ❓How many known security vulnerabilities does your application have?
  • ❓Do you remove dead code and unused operating system packages and libraries?
  • ❓How often do you / your team upgrade the versions of the software you're using?
