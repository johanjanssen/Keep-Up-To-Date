Native Images vs. CRaC

Four Ways to Package a JVM App

Same app, four different runtime shapes

ApproachWhat it is
Normal JRE imageA full, unmodified JVM: the default Docker base image
jlink runtimeStill a real JVM, but custom-built with only the modules your app needs
CRaC checkpointStill a real JVM: restored from a snapshot of an already-warmed-up process
GraalVM native-imageNo JVM at all: ahead-of-time compiled to a native binary

The first three still run on a JVM; native-image is the odd one out: that's the dashed path in the next diagram.

CRaC's tradeoff isn't compatibility; it's operational: the checkpoint captures process state (open sockets, files) at a point in time, so you design your startup code around what's safe to snapshot.

🛠️ It's Not Just a Java Problem

Fast-startup / low-footprint runtime strategies across ecosystems

Every language faces the same "does my image need a full runtime?" question: the shape of the answer just differs.

Tool / LeverLanguage / EcosystemNotes
jlink custom JRE, GraalVM native-imageJava (also polyglot: JS, Python, Ruby)AOT-compiles to a native binary, or trims the JRE to drop the JVM entirely
Azul CRaCJava / JVMCheckpoint/restore a warmed-up JVM instead of recompiling it
CRIUAny (OS-level process checkpoint)The Linux checkpoint/restore mechanism CRaC itself builds on
Native AOT / ReadyToRun.NET.NET's direct equivalent of GraalVM native-image, plus pre-JIT for faster cold start
Static binariesGo, RustCompiled to a single static binary by default (scratch/musl "just works"): no runtime image or JIT warm-up needed
Slim/alpine/distroless base imagesPython, Node.jsInterpreted: always need a runtime layer, so the lever is a smaller base image, not dropping it
V8 startup snapshotsNode.jsSnapshots the initialised heap to skip re-parsing/re-executing startup code

Java and .NET need an explicit AOT step to reach what Go and Rust get by default; interpreted languages can't get there at all, only smaller.
