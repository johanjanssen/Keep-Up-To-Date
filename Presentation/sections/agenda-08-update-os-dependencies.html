Chapter 08

Update OS Dependencies

🐳 The Layer You Forgot

Every containerised application is built on a base image. That base image is a dependency: one that changes constantly, carries OS-level CVEs, and is easy to forget about.

  1. You wrote FROM mybase:v2 six months ago
  2. That tag now points to a different image: rebuilt with OS patches
  3. Your CI uses the cached layer from six months ago
  4. You are running vulnerable OS packages, and you don't know it

Ride the Release Train

Modern runtimes and languages ship on a predictable cadence: not when they feel ready, but on a fixed schedule.

  • 📅Regular releases → smaller, manageable changes each time
  • 🛡️LTS (Long-Term Support) releases get extended security patches: safe for production
  • 🧪Non-LTS releases are production-quality for short-lived or internal services

Update FROM in Dockerfiles

Treat the base image tag like any other dependency version: bump it deliberately, on a schedule, not by accident when the tag silently moves underneath you.

☕ Java example 
- FROM eclipse-temurin:21-jre
+ FROM eclipse-temurin:25-jre
A one-line diff, but it pulls in the latest JVM, security patches, and OS package updates all at once.

Why Pin at All?

Whether it's a Docker base image, a language runtime, or a build tool, floating version tags silently change under you. Pinning trades that surprise for a few concrete guarantees:

  • 🔁Reproducible builds: the same tag produces the same bytes today and six months from now
  • ⏪Rollback: revert to an exact known-good version when a release breaks something
  • 🐞Debugging: you know precisely what's running, so "works on my machine" isn't a mystery
  • 📋Auditability: prove exactly what shipped, for security reviews, incident response, and compliance

A Specific Tag Still Isn't Immutable

It's tempting to think eclipse-temurin:25.0.4_7-jre-ubi10-minimal is "specific enough" to be safe. It isn't: a Docker tag is just a mutable pointer, and the maintainer can repoint it whenever they rebuild the image.

✅ Maven: release = immutable

Once 25.0.4 is published to Maven Central, that artifact can never change. Republishing the same coordinate is rejected.

❌ Docker: a tag can move

eclipse-temurin:25.0.4_7-jre-ubi10-minimal can be rebuilt and re-pushed: new OS packages, same tag, different bytes.

So the only truly immutable reference is the image digest (@sha256:...), not the version tag.

The Same Tag, Two Different SHAs

Pinning by digest is safer, but the digest itself isn't a single global truth: Docker Hub and your local Docker cache can disagree on which SHA a tag currently points to.

  • ☁️Docker Hub always shows the current digest for a tag: whatever was last pushed.
  • 💻Your local cache keeps whatever digest you pulled last: it doesn't refresh on its own.
  • 🧭Two developers (or dev vs. CI) can end up building from different SHAs for the "same" tag, just because they pulled at different times.
☕ Java example Always resolve and record the digest explicitly (docker pull + docker inspect --format='{{index .RepoDigests 0}}'), then commit that exact @sha256:... to the Dockerfile: don't rely on whichever SHA happened to be cached.

Pin Versions, Not Floating Tags

Whether it's a Docker base image, a language runtime, or a build tool, floating version tags silently change under you.

❌ Floating: dangerous 
FROM eclipse-temurin:25-jre
# Rebuilt weekly. CI uses a stale
# cached layer from months ago.
✅ Pinned: reproducible 
FROM eclipse-temurin:25-jre\
@sha256:7ea65de6...
Use automation to update the pin via PR.
☕ Java tooling Commit .sdkmanrc (java=25.0.1-tem) and mvnw / gradlew wrappers: everyone and CI run the exact same versions.

🤖 Manual Updates Don't Scale

As a project grows, the number of dependencies that need attention grows faster than the team's capacity to review them.

  • 🤖Dependency bots watch registries continuously and open PRs automatically
  • 📋The policy (what to group, what to auto-merge, what needs review) lives in config: not in people's heads
  • ✅CI verifies each update before it lands: humans only intervene for breaking changes

Policy as Code

🔧 Renovate config: renovate.json, checked into the repo

Define how updates are handled in a config file committed to the repo: not in a wiki, not in a person's memory.

// renovate.json
{
  "extends": ["config:base"],
  "packageRules": [
    {
      "description": "Group all Docker base-image bumps: one PR, one review",
      "matchDatasources": ["docker"],
      "groupName": "Docker base images",
      "schedule": ["every weekend"]
    },
    {
      "description": "Auto-merge patch-level OS package bumps once CI is green",
      "matchManagers": ["dockerfile"],
      "matchUpdateTypes": ["patch"],
      "automerge": true
    }
  ],
  "vulnerabilityAlerts": {
    "labels": ["security"],
    "automerge": true   // immediate: security patch + green CI = merged
  }
}
