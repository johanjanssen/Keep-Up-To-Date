com.h2database:h2 false positive — needed at runtime

DatabaseController opens a JDBC connection via java.sql.DriverManager and queries it (see /db-check) — h2 IS used, but only through the JDBC 4 ServiceLoader mechanism (h2's jar ships META-INF/services/java.sql.Driver, so the driver self-registers). No class from org.h2.* ever appears in this project's own bytecode, which is all dependency:analyze can see.

pom.xml — before
<dependency>
            <groupId>com.h2database</groupId>
            <artifactId>h2</artifactId>
            <version>2.4.240</version>
        </dependency>
pom.xml — after (dependency unchanged)
<dependency>
            <groupId>com.h2database</groupId>
            <artifactId>h2</artifactId>
            <version>2.4.240</version>
        </dependency>
pom.xml — add to <build><plugins>
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-dependency-plugin</artifactId>
    <configuration>
        <usedDependencies>
            <usedDependency>com.h2database:h2</usedDependency>
        </usedDependencies>
    </configuration>
</plugin>

→ Keep the <dependency>. Instead, tell the plugin explicitly that it's used by adding a <usedDependencies> entry to maven-dependency-plugin's <configuration> — the supported way to suppress a bytecode-analysis false positive without deleting a dependency the app actually needs.

Why this matters

dependency:analyze compares declared dependencies against compiled bytecode — it can only see direct class references. Reflection, SPI/ServiceLoader lookups (JDBC drivers, logging bridges, most annotation processors), and dependencies pulled in purely for their META-INF contents are all invisible to it. Treat every finding as a starting point for a human decision, not an automatic deletion: real dead weight should go, but a dependency the app genuinely needs at runtime should be kept and the warning suppressed explicitly via <usedDependencies> instead.
